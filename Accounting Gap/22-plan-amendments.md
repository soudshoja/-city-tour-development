### 1.3 The nine orchestrator decisions this document implements

These are binding inputs, not proposals. They are restated here so the phases in §2–§3 can cite them by id.

| id | Decision (condensed) |
|---|---|
| **D1** | The per-agent liability is the agent's **contractual earnings** — not the case profit. Agent types: 1 Salary (no commission), 2 Commission (rate × task profit), 3 Both-A (commission + salary), 4 Both-B (target-gated pool). "Per-case profit the agent monitors" is a **reporting dimension** (the agent's cost centre on every line), never a liability. The type-4 formula lives in **one** service used by both posting and report. **Rule 1e (orchestrator ruling A10, DECIDED — closes Q-20.1):** "task profit" for commission purposes means **gross margin** — sell price minus supplier cost, computed **before** any agent-borne charge (gateway fee, negative margin, ADM) is deducted. What the signed contract says the *rate* applies to (its actual number) is still a fact only the owner knows — that stays open as **§7 Q3**. |
| **D2** | **Two balance-sheet leaves per agent**, same depth, never netted in the ledger: an *Agent Commission Payable* leaf under `2230`, and an *Agent Receivable* leaf under a new group inside `1350 Accounts Receivable`. Net only on the statement footer. Salary stays pooled in `2201` with `doc_type` **HRJV**, gated by a payroll permission. **Codes now locked (orchestrator ruling A4, supersedes the "doc 20 owns the codes" deferral):** the Agent Receivables group is **`135900`**, the Airline Incentive Receivable leaf is **`135800`**, and per-agent leaves mint as **`135901…`** (receivable) / **`223001…`** (payable, unchanged). **Hard ordering gate:** **P5.3.A depends on W3.A** — W3.A's `ensurePartyLeaf()`/`AccountCodeGenerator` path must be live and the legacy `AgentController` generators deleted *before* P5.3.A mints the first `135900` group, or the legacy `max(sibling)+1` generator mints `135901` itself and collides with the very leaf P5.3.A is about to create (§2.1c, §6.1). |
| **D3** | **Charge-nature rule.** Charges *arising from earnings* (gateway-fee share, negative margin, refund clawback, ADM pass-through) reduce **Agent Commission Payable first**, overflow → **Agent Receivable**. Charges *unrelated to earnings* (loan, services bought on credit) → **Agent Receivable directly**, as an open item that **ages**. Collection method is a company decision **per settlement**, never automatic. |
| **D4** | **ONE bearer policy model.** Per company, per charge kind ∈ {`gateway_fee`, `negative_margin`, `refund_clawback`, `adm`}: bearer ∈ {`client`\|`company`\|`agent`\|`split`} + `agent_percentage` (default 50), with per-gateway / per-method override for `gateway_fee`. **Client-bears is a pricing option (gross-up), not a posting variant**: the fee expense is ALWAYS booked in full to the gateway-charges leaf; recovery from client → *Gateway Fee Recovery*, recovery from agent → *Gateway Fee Recovery (Agents)*. | **D5** | **ADM/ACM are documents** (memo module: DBN/CRN header + lines, own `SequenceService` series, party, `ticket_number`, `pnr`, `airline_id`, `BSPTYPE` ∈ ET\|VOID\|REFUND\|ADM\|ACM\|EMD (orchestrator ruling O5 restores `VOID` to the vocabulary), reason). **Two-step**: airline memo first (ADM: Dr Airline Memo Control / Cr airline payable; ACM inverse), then — if bearer = agent/split — an **agent DBN** (Dr agent per D3 / Cr Airline Memo Control). BSP reconciliation consumes the memos per ticket. Incentive accrual clears against the ACM. |
| **D6** | **Agent-as-customer**: an agent may hold a linked client record (`agents.client_id`). Sales to it route the **receivable leg to the agent's receivable leaf** instead of the pooled Clients leaf; everything else is a normal sale. |
| **D7** | **Credit control per party** (client *and* agent): credit limit + credit-from date + blacklist. Enforcement mode is a company option {`warn`\|`block`}, default **block** for sales on credit. Balances recomputed from open items. |
| **D8** | **Reporting spine**: ledger integrity (W3/W4/P3) → canonical `LedgerReportQuery` (P5.4) → statements. The agent statement is **two ledgers side by side** (payable, receivable) with brought-forward rows + ageing, netted **in the footer only**; it reads the **LEDGER** by `invoice_id` as the single source of truth. `invoice_details.profit`/`commission` become **stored mirrors**. |
| **D9** | Blueprint coverage decisions from 21 §6: monthly balance buckets **deferred with a measured ceiling** (P5.16); full audit `*_log` history **YES** (P5.17); draft→review→post **YES** (P5.1); attachments registry **YES** (P7); password/session policy **reinstated** (P7); six typed roots + `AccGroup` rollup **at COA-template time** (P7); payroll confidentiality gate **NOW** (HRJV + permission); ticket stock control = company option **OFF by default** (e-ticket/BSP agencies get serial-gap detection only); BSP reconciliation ships in **P7.5** (amend 15 §F); management report variants: ship the four **dimensions** the blueprint names — by customer / airline / consultant / service — in the **detailed** form first; other dimensions and the comparison / variance / top-N presentations are terminal. |

### 1.5 Multi-tenant framing (orchestrator addendum S7)

This is a **complete multi-tenant SaaS product**, not a bespoke ledger for one agency. Every option this document registers (§4) is a **per-company** setting with a stated default — **no option may be resolved globally**, and every value a company can pick must post correctly for that company alone, independent of what any other tenant on the platform has chosen. The `travel-accounting-system` skill blueprint is a **reference** consulted for posting shapes and report structure — it is never the target: where it models something as a single fixed mechanism (one commission account, one bearer, one settlement mode) and this product needs a company-configurable one, the option register wins and the blueprint's shape is the *default* value, not the only one. Every phase in §2–§3 that resolves "how does X post" must resolve it **per company**, never by reading a constant.

### P5.12 — Credit control (D7)

**Goal.** Stop a sale on credit to a party that is already over its limit or blacklisted. 21 §3 N9 calls this "the biggest pure gap in the matrix": our audit noticed it and wrote a recommendation, but it never received an MF-id or a phase, so no wave owns it. `clients.credit` is a **prepaid top-up balance**, not a limit (19 §3d), and `credit_facility` is dead schema.

**Depends on:** P5.3 (per-party accounts and open items — you cannot recompute a balance from a pooled leaf), **P5.3.F** (the B2B/B2C party-type distinction, addendum S4 — which parties even carry a credit-control-relevant type).

**Deliverables.**
- Per-party credit fields on **both** parties (D7): `credit_limit`, `credit_from_date`, `is_blacklisted`, on `clients` and on `agents` (the agent columns are in doc 20 §3.2's migration).
- `CreditControlService::assess(partyType, partyId, proposedAmount)` returning `{current_balance, available_credit, verdict}` where `current_balance` is **recomputed from open items** (P5.3's `settled_amount`), never from a stored mutable column.
- Enforcement at **invoice save** (blueprint 03 §8), driven by `accounting.credit_control.mode ∈ {warn, block}` — default **block** for sales on credit (D7, §4.2). **`off` is not a legal value (orchestrator ruling O3)**: a company that wants no control at all expresses it per-party by leaving `credit_limit` null (§4.2), not by disabling the mode for everyone — the mode always runs, it just never blocks a party with no stated limit. Blacklist is a hard stop regardless of mode.
- Whether the agent's own limit applies to Rule-6 sales is doc 20 **O10** (`agent_credit_control_applies`, default `on`) — carried in §4.2.
- Cash / prepaid sales are never blocked — the gate applies only when the sale creates a receivable.
- **Opening journals are excluded** from the balance (blueprint 03 §8), mirroring doc 20 §5.16's rule that `Balance B/F` lines are excluded from ageing. Without that exclusion a carried-forward balance is counted twice on 1 January.
- The available-credit figure appears on the party statement (D8) and on the credit-control exception report.

## 4. COMPANY OPTIONS CATALOGUE

**The register.** Every business preference that becomes a setting lives here. Two rules follow from the owner's standing instruction that his scenarios become *company options*:

1. **No phase may hard-code a value that appears in this table.** If a posting path needs to know who bears a fee, it asks the policy; it does not branch on a constant.
2. **Every option value must post correctly.** An option whose value produces books that do not balance, or a liability that misstates what is owed, is not an option — it is a bug with a dropdown. Each row states the posting effect **per value** so that this is checkable. Where a value cannot post correctly yet, the row says so and the value is **refused at save** until its phase lands (see `accounting.vat.enabled`).

### 5.3 A third conflict, found while writing this: two parallel bearer tables

Not in 21, and it must not be inherited into P5.13.

Two tables exist **today** with the same shape and the same purpose:

- `agent_loss` (model `AgentLoss`) — `loss_bearer ∈ {company, agent, split}`, `agent_percentage`, `company_percentage`, `unique(agent_id, company_id)`, with `calculateLossDistribution()` and `getForAgent()` defaulting to company-bears.
- `agent_charge` (model `AgentCharge`, migration `create_agent_charge_settings_table`) — `charge_bearer ∈ {company, agent, split}`, identical columns, identical unique key, whose docblock says it covers "Gateway charges + Supplier surcharges".

Doc 20 §10.17 counts **four** places the same concept lives: these two, plus `invoices.agent_loss`/`company_loss` as a per-invoice override, plus `charges.paid_by` / `payment_methods.paid_by` with only `Client|Company` and no agent at all. D4 mandates **one** policy model. Two tables with one unique key each also make it structurally impossible to express D4's per-charge-kind policy (you cannot hold different bearers for `gateway_fee` and `adm` for the same agent).

**Resolution — schema corrected, orchestrator ruling O11.** Consolidate onto `agent_charge_policies`, keyed **`(company_id, agent_id nullable, charge_kind, scope_key nullable)`** — `agent_id NULL` being the company default — with `bearer` and `agent_percentage`. **Revision 2's `payment_method_id nullable, gateway nullable` columns are dropped from this table entirely**: the per-gateway/per-method override for `gateway_fee` lives instead on `charges.paid_by` / `payment_methods.paid_by`, whose vocabulary is extended from `Client|Company` to **`Client|Company|Agent|Split`** (with a method-level `agent_percentage` column, read only when `paid_by = Split` — B9) in the same migration — the policy table governs *bearer defaults by charge kind*, the two `paid_by` columns govern *pricing-time overrides*, and conflating them made the table impossible to key cleanly. `scope_key` carries the one genuine second dimension that remains: the same `charge_kind` recurring in a different context (O13's `gateway_fee, scope_key = 'settlement'`).

**Backfill, corrected — orchestrator ruling O12.** Migrate `agent_loss` rows to **`negative_margin` ONLY** — **never** `refund_clawback`. Revision 2 migrated each row to *both*, reasoning that "the old model could not distinguish them"; that is true, but it does not follow that both destinations should get a row. `refund_clawback` under the new three-event model (A3) is a materially different, newer concept — a recovery against a brand-new `5125` clawback leaf that `agent_loss` never touched or knew about — and manufacturing a `refund_clawback` policy row that has no historical basis misrepresents what was actually agreed with that agent. Delete **`BearerMigrationTest::an_agent_loss_row_becomes_both_a_negative_margin_and_a_refund_clawback_policy`** from the acceptance list below; it asserts exactly the behaviour this ruling forbids. `agent_charge` rows still migrate to `gateway_fee`; `adm` still has no historical equivalent and seeds at `bearer = company`, **which the owner must be told** (doc 20 §8.3). `charges.paid_by` / `payment_methods.paid_by` stay as the client-facing pricing flags they already are (now with `Agent` added, above); `invoices.agent_loss`/`company_loss` stays as a per-document recorded exception. `company_percentage` is dropped: it is derived (`100 − agent_percentage`), and storing both invites the two to disagree.

### 10.5 Decisions (mine, blueprint silent) — carried from the brief verbatim

These are orchestrator decisions, not open questions, exactly as the brief states them:

- **FX.** Reversal posts at the **original sale rate**; any difference against the payout rate is a realized FX line on the disposition PV, never folded into the reversal.
- **Markup symmetry.** The CRN's markup line reverses symmetrically by default. New company option **`refund_retain_markup`** ∈ `{on, off}`, default **`off`** (§10.7).
- **Period close.** A refund raised after the original sale's period has closed is dated **today**, in the currently open period, and links back to the original — the closed period is **never reopened**.
- **Agent-purchased ticket.** Same refund document; the AR leg is the agent's own receivable leaf (`1359xx`). **No commission un-earn** — none was ever earned on an agent's own purchase (§4.1 `commission_on_own_purchase`, default `off`; Q-20.5).
- **Penalty validation.** The penalty must be `≤` the original cost. Auto-populated from the AIR `RF` line or an ADM parse when present; a manually entered penalty requires an approver.
- **Partially-paid invoice.** The CRN reduces the invoice's open item first; any client-net **excess** beyond what was actually paid goes through the disposition step (f), same as a fully-paid sale.

### 11.1 Scope ruling — overrides §2.3's narrow W5

**§2.3 as written scheduled only one thing into W5:** the `cheque_clearance_date` column plus persisting the five instrument fields at approval time, with the PDC workflow, FX line, bank-charges line, refund/keep-as-advance and staff/expense PV explicitly deferred to P5.18. ### 11.2 W5 deliverables — W5.L → W5.R → W5.P → W5.S → W5.X (sequential)

**W5.L — LineDraft / engine prerequisites.**

**W5.R — Receipt Voucher through the seam.** `ReceiptVoucherController::store/update/approve/delete` build a `DocumentDraft` (`doc_type = RV`, `sub_type`, instrument fields) and call `PostingSeam::post()` — balanced or rejected, no `Log::error`-and-continue. A cheque instrument dated after the voucher date debits **`1215`** against AR; clearance (a manual action that sets `cheque_clearance_date`) debits the bank leaf and credits `1215`; a bounce reverses the clearance and raises a bounce-fee DBN to the client. `update()` reverses and reposts a new draft; `delete()` reverses; both are refused when any line is `reconciled` or the period is locked (`checkLocked`). The import-approval branch's `actual_balance +=` hand-increment is **killed**. All name-`LIKE` account lookups (`'Accounts Receivable'`, `'Clients'`, `'Receipt Voucher Cash'`, `'Bank Accounts'`) are killed with it. `PaymentReceiptService::generateAndSendPdf()` still fires on approve when `receipt_send_on_payment`. **W5.P — Payment Voucher through the seam.** Same pattern, `doc_type = PV`. The bank-balance pre-check moves inside the transaction, reading `TrialBalanceService` instead of a raw `SUM(debit)-SUM(credit)` — killing the TOCTOU race `w5-state.md` §1 flagged — gated by a new option **`pv_allow_overdraft`**, default `false`. **W5.S — legacy `AgentSettlementService`.** `settleByProfit()` / `onPaymentCompleted()` route their JE writes through the seam as `doc_type = AST`, `sub_type = LEGACY` — **not** a PV, and not a new private series: a **temporary `AST/{branch}/{yy}/{seq}` serial schema is created now**, so P5.13's real `AST` build inherits the series rather than migrating one. **What this section is.** New ground only — the full design for the void wave §2.4 only sketched: the two-leg model, the five kinds (VOID, AUTO_VOID, VOID WITH FEE, REISSUE, BULK VOID), commission rules, preconditions and idempotency, the `TaskStatusService` consolidation, the bundled fixes it ships with, the two new fee leaves, and the options it registers. **Nothing in §1–§11 is rewritten.** Where this section narrows or supersedes something §2.4 already printed (the void-fee leaf names, the reissue mechanics, the bulk-void shape), the earlier text is left as written and this section states the current, authoritative design going forward — the same append-only rule §10 and §11 used.

### 12.1 Model — two independent legs

Every void or reissue carries two legs, never conflated:

- **Ticket leg** (`tasks.ticket_status` ∈ `issued\|void\|refunded\|reissued\|emd`) — supplier truth: `reverse()` of the original cost/payable document, keyed on `(task_id, doc_type)`, `transactions.bsptype = VOID\|ET`.
- **Client leg** (`tasks.client_status` ∈ `open\|credited\|refunded\|rebilled`) — CRN reverse of the sale lines on the invoice carrying the task, then a fee DBN if any, then disposition of any paid amount per `invoice_overpay_cancel_policy` (INV-1, §10.1 — reused, not a new key): `credit → 2632` \| `refund_out →` PV draft \| `manual`.

Both columns are **additive** — `tasks.status` stays for legacy readers; `ticket_status`/`client_status` are new nullable columns backfilled from `status`. Never touch journal rows by description; never delete one. Invoices flip status via engine hooks: `cancelled` when every task on it is void, `partial refund` when some are.

### 12.2 Kinds

| Kind | Mechanics |
|---|---|
| **VOID** | Same-day/pre-settlement, no airline penalty. Ticket leg `reverse()`; client leg full CRN; disposition per `invoice_overpay_cancel_policy`. `sub_type = VOID`. |
| **AUTO_VOID** | `ProcessExpiredConfirmedTasks`'s expiry of a confirmed-not-issued task. Never invoiced → status flip only, **no ledger touch**. Invoiced → same as VOID, `sub_type = AUTO_VOID`. The command goes through `TaskStatusService::void()`, never a raw `save()` — this is what fixes ct-void-map §7 bug 8 (the command flipped status directly, bypassing financials and `original_task_id`). |
| **VOID WITH FEE** | As VOID, plus a DBN: `Dr AR / Cr 4134 Void Fee Income` (fee = a `service_type = 'fee'` sale, line `reason_tag = fee`). Fee amount defaults from the company fee table, reusing W4's `fee_table`/`refund_fee_override` options (§10.6) rather than minting a second pair. `commissionable_fee_types` decides whether the fee also carries an agent-commission JV. |
| **REISSUE / EXCHANGE** | Reverse the original sale + cost, linked (`sub_type = REISSUE_REVERSAL`); post the new task's sale + cost as new lines on the **same** invoice (`sub_type = REISSUE`). The fare difference is the **net** of the new lines against the CRN, shown as a DBN (client owes) or CRN (client credited) — **never folded into a rewritten total**, restating §2.4's original rule. Reissue fee → **4135 Reissue Fee Income**. Existing receipt allocations on the invoice re-apply to the new lines through the apply engine automatically; any remainder goes through the same disposition step. `switchInvoiceTask()` becomes a thin wrapper over this flow — its profit delta, today only logged (ct-void-map §4), now actually posts. |
| **BULK VOID** | `POST /tasks/bulk-void` — **one** outer transaction, all-or-nothing by default (restates §2.4's O6 lock, unchanged); new option `bulk_void_mode` ∈ `{atomic \| per_task_report}`, default **atomic**. | id | Ruling |

### 14.2 The three-layer model (binding, restated from the design doc)

1. **Posting immutability** — always true, in every period. A posted entry is never edited or deleted; correction is reverse + repost, from the instant it posts.
2. **Period close** — a date-range control on `docDate`, monthly. Once a month is `locked`, no new entry may be dated into it. `PeriodGuard::assertOpen()` is the single enforcement point, already called by every feeder through `PostingService`/`PostingSeam`.
3. **Reconciliation lock** — protects one matched `journal_entries` line inside an otherwise-open month. It does **not** close a period, and it is not a substitute for layer 2's gate.

### 14.3 Rule for W4/W5/W6 (and any later wave)

Because every document a wave posts already routes through `PostingService`, period enforcement is **free** once `PeriodGuard` ships real logic — no wave builds its own period check. What each wave owes instead: pass the correct accounting document date into every `DocumentDraft`, and never set `allowLockedPeriods` to bypass the guard without saying so explicitly in its report. `checkLocked()` stays exactly where waves already call it (Layer 1's per-record pin) — it is not deprecated, it just was never the period gate. `w4-brief.md`, `w5-brief.md`, and `w6-brief.md` were corrected directly 2026-08-28 to state this split; this section is doc 22's own record of the same correction.

`ReportController::profitLoss` still periodizes by `created_at`, not `transaction_date` (BUG-C4, doc 08 §BUG-C4, fixed at **P5.4**). Monthly close's entire premise — "once the monthly P&L is calculated, the period is locked" — reads that P&L off whichever query is live at close time. Closing a month against a P&L bucketed on `created_at` closes on the **wrong entries** for any document posted with a `transaction_date` in one month but a `created_at` in another (a common shape here: late-arriving supplier cost, a reissue/refund posted today against an earlier sale, a backdated-then-corrected entry). **BUG-C4 must be resolved before real monthly close (the close command/checklist in `PeriodGuard`'s dedicated phase, per the design doc §7) ships or is trusted** — this is a hard dependency, not a scheduling preference, and is recorded here so the close-command phase does not start ahead of P5.4.

### 15.1 HEADLINE — sale posting basis: ticket-type services must post NET

**[blueprint `04-travel-industry.md` §4 "SellValue = Payable + Income"] + [accounting principle: IFRS 15 principal/agent — a BSP agency does not control the flight, so revenue = margin].** The blueprint books a ticket sale as `Dr Customer (sell) / Cr Airline Payable (cost) / Cr Income (margin)`; fare, tax and BSP amounts are statistical fields on the ticket, never revenue lines. Discussion during this wave described our current W3c ON-path shape as **gross** — `Cr Revenue` for the full sell price, with a separate `Dr Cost of Sales` — and a read-only audit is in flight (`.planning/accounting-waves/w3/sale-shape-audit.md`) to confirm the exact lines as built. This section's decision stands regardless of that audit's finding:

**[company option]** `service_type.posting_basis` ∈ `{agent, principal}`, resolved **at posting time**, one value per service type:
- `agent` (NET posting — `Dr Customer / Cr Cost Payable / Cr Income`, margin only in revenue) — **default** for `flight`, `rail`, `ferry`, `esim`, `insurance`, `visa`, `lounge`. These are services the agency arranges but does not control (IFRS 15 agent indicators: no inventory risk, no price-setting discretion, the airline/insurer/issuer is the obligor).
- `principal` (GROSS posting — full sell as revenue, separate cost-of-sales line) — **default** for packages the agency assembles itself: `tour`, own-inventory hotel block. These are services where the agency does control the good/service before transferring it to the client (IFRS 15 principal indicators: the agency is primarily responsible for fulfillment, bears inventory/pricing risk).

Gross turnover for BSP reports, segment/incentive counts, and airline-volume calculations is reconstructed from the ticket's **statistical fields** (fare, tax, BSP amount — already on the document under the blueprint's model), never from a revenue account. This is unaffected by which basis is used for the ledger, because those reports never read the ledger's revenue line in the first place.

**Superseded idea, recorded as withdrawn.** An earlier framing (discussion during this wave) proposed keeping **gross in the ledger unconditionally** and adding a report-level `revenue_presentation` ∈ `{gross, net}` toggle that only changed what the P&L *displayed*. **This is withdrawn.** [accounting principle] The blueprint books net **at posting**, not at reporting time — a report-level toggle leaves the trial balance and every underlying ledger account wrong (revenue overstated, cost of sales overstated by the same amount) regardless of which report presentation a user later selects, which is a materially different and inferior outcome to booking the correct amount once, at the source. `revenue_presentation` does not exist as a company option after this revision; it appears in §15.7 only as the record of what was withdrawn and why.

**Correction owed.** The current W3c sale-draft shape needs to be checked against this decision and corrected if it posts gross for an `agent`-basis service type. This is **flagged for a new fix lane, W3d**, to run after the current W3 gate closes — not folded into W3 itself, so it doesn't block or reopen work already in flight. **W4/W5/W6 are unaffected**: refund, un-earn, disposition, and period-lock mechanics produce the same P&L outcome under either basis (the same total margin moves through the same accrual/reversal machinery); only which lines carry the turnover and cost amounts differs. See §15.7/§15.8 for the doc 11 pointers.

### 15.2 Three-date model

**[accounting principle / standard ledger practice]** Three dates, not two:
- **(a) `transaction_date`** — the document date, printed on the document, exists today, never falsified after the fact.
- **(b) `posting_date`** *(NEW column)* — the accounting period the entry actually hits; drives P&L, trial balance, and `PeriodGuard`.
- **(c) `created_at`** — audit-only, never drives reporting or the period gate.

**Rule:** `posting_date = transaction_date` if that period is open; otherwise `posting_date` = the earliest open period, and `transaction_date` is never changed. `PeriodGuard::assertOpen` validates `posting_date`, not `transaction_date`.

**[owner example]** A Feb-10 invoice entered March 5, after Feb has closed: `transaction_date` stays Feb 10; `posting_date` becomes March, and the invoice lands in March's P&L. This is the fix path for BUG-C4 (P&L periodized on `created_at` today; P5.4 must periodize on `posting_date` instead). Full mechanics: `.planning/accounting-waves/period-lock-design.md` §8 (§15.7 records the cross-check).

### 15.3 Dependency-aware unlock

**[accounting principle: audit trail / immutability]** The dependency chain is invoice → applications/allocations → receipts → reconciled bank lines → closed period; any locked or reconciled descendant, or a closed period containing the entry, blocks unlocking an ancestor. Unlock requires permission + a mandatory reason + an audit record (who, when, why, what was downstream at the time).

**Unlock is the exception, never the correction path** — the normal correction is reverse + repost in the currently open period, which needs no unlock because it leaves the original entry untouched. Unlock exists only for a genuine data-entry error caught before any downstream consumption.

**[owner example]** Editing an invoice whose only line is already reconciled must be refused — the dependency check stops at the reconciled leaf; the correction is reverse + repost, not an edit and not an unlock. Full mechanics: `.planning/accounting-waves/period-lock-design.md` §8.2.

### 15.4 Bearer policy on the agent profile, effective-dated

**[company option]** Bearer policy moves to the same settings area as commission/salary terms, resolved **company default → agent profile type (1–4: Salary, Commission, Both-A, Both-B) → per-agent override** — a new tier inserted into `bearer-matrix-design.md` §2's precedence chain (doc 20 §4). Every policy row carries an `effective_from` date, and every posted document that consults `BearerResolver` snapshots the resolved bearer + `agent_percentage` onto itself at posting time — never re-derived live on replay or report.

**[accounting principle: locked periods must remain reconcilable to the policy that applied]** Without the snapshot, editing an agent's policy later would silently change how an already-`locked` month's documents are understood, which a locked period must never permit. Cross-ref: `.planning/accounting-waves/bearer-matrix-design.md` §2 (precedence tier) and §6 (effective-dating + snapshot mechanics, doc 20 owns the `agent_type`/`effective_from`/snapshot columns per bearer-matrix-design.md §2's ⚠ convention).

### 15.6 Revenue recognition timing per service type

**[accounting principle: IFRS 15]** `at_issue` for agent-type services — the performance obligation (arranging the booking) is satisfied at ticketing. `at_travel` for principal-type services — a deferred-revenue liability is booked at sale and released on the travel date by a scheduled engine job; the cost side mirrors it (prepaid-cost asset or accrued-supplier-cost liability at sale, released to COGS on the same schedule).

**[company option]** `service_type.revenue_recognition` ∈ `{at_issue, at_travel}`, defaulting **the same way §15.1's `posting_basis` defaults do**: `at_issue` for every `agent`-basis service type (`flight`, `rail`, `ferry`, `esim`, `insurance`, `visa`, `lounge`), `at_travel` for every `principal`-basis service type (`tour`, own-inventory hotel block). This must be decided before dev cutover — it changes which month profit lands in, and months get locked (§15.2) on whatever the recognition rule produced. The blueprint is silent here (books at invoice date only); this is a decision this project's monthly-lock design requires that the blueprint's annual-only close never needed to make.
